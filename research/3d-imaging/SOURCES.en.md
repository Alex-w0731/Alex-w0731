# 3D imaging workflow: sources and design references

[中文](SOURCES.md) · [Workflow guide](GUIDE.en.md)

Verification date: **2026-10-02**. This page draws on the project authors' GitHub repositories, official documentation, and license files. The review covers publicly documented capabilities and usage boundaries; these tools have not been installed locally, independently benchmarked, or clinically validated for this review.

This workflow is intended for volumetric research microscopy data. The browser page is a **workflow planner and synthetic-data demonstration**, with no real AI inference backend. Model names, processing nodes, and example images do not indicate that external tools have run. See [GUIDE.en.md](GUIDE.en.md) for the usage guide.

## Six main reference projects

| Project and official sources | Verified capabilities | Ideas adopted in this workflow | Licensing and practical limits |
|---|---|---|---|
| **napari** · [GitHub](https://github.com/napari/napari) · [Image layer](https://napari.org/stable/howtos/layers/image.html) · [Labels layer](https://napari.org/stable/howtos/layers/labels.html) | Multidimensional image, label, point, track, and surface layers; 2D slice and 3D viewing; support for arrays such as Dask/Zarr. | View images, automatic labels, and manually corrected labels together. Locate regions in a global low-resolution 3D view, then review ROIs and orthogonal slices at the original resolution. | [BSD-3-Clause](https://github.com/napari/napari/blob/main/LICENSE). The official stable documentation states that multiscale rendering primarily supports 2D; in 3D, only the lowest-resolution level is displayed. Labels cannot be edited directly in 3D display mode or as multiscale data. A brush can span three dimensions during slice editing; this is not painting in the 3D rendered view. |
| **OME-Zarr / ome-zarr-py** · [GitHub](https://github.com/ome/ome-zarr-py) · [Official documentation](https://ome-zarr.readthedocs.io/en/stable/) · [Writer source and parameter documentation](https://github.com/ome/ome-zarr-py/blob/master/ome_zarr/writer.py) | Organizes multiresolution biological images according to OME NGFF. The writer supports NumPy/Dask pyramids, axes, physical sizes, units, and coordinate transformations. | Store image data and labels in separate layers. Use chunks and pyramids to reduce the need to read entire datasets, explicitly preserving axis order, voxel spacing, and units. | [BSD-2-Clause](https://github.com/ome/ome-zarr-py/blob/master/LICENSE). The format does not automatically generate complete analysis provenance; parameters, versions, checksums, and manual edit history must be saved separately. Pin and verify NGFF versions and reader compatibility. A directory ending in `.zarr` does not by itself establish OME-Zarr compliance. |
| **BigStitcher** · [GitHub](https://github.com/JaneliaSciComp/BigStitcher) · [Official ImageJ documentation](https://imagej.net/plugins/bigstitcher/) · [PSF management](https://imagej.net/plugins/bigstitcher/psf) | Registration and fusion of microscopy tiles and views, with interactive inspection of intermediate steps; multiview reconstruction and PSF-based deconvolution. | Divide stitching into pre-alignment, local matching, global optimization, seam review, and fusion. Retain project XML and transformations rather than saving only the final fused image. | [GPL-2.0](https://github.com/JaneliaSciComp/BigStitcher/blob/master/LICENSE.txt). Requires real overlap and reliable signal; cannot automatically repair missing acquisitions. Deconvolution needs a PSF compatible with the optical conditions. The official ImageJ documentation notes that some migrated pages have not been reviewed again; use the interface of your pinned version as the operational reference. The former PreibischLab repository address now redirects to JaneliaSciComp. |
| **multiview-stitcher** · [GitHub](https://github.com/multiview-stitcher/multiview-stitcher) · [Official documentation](https://multiview-stitcher.github.io/multiview-stitcher/) | Python-native 2D/3D registration and chunked fusion; integration with Dask/Zarr/xarray, napari, and related tools; replaceable registration and fusion functions. | Provide a Python batch-processing route, compare coordinate systems from stage metadata and registration results, and integrate large-volume stitching into scripts with recorded parameters. | [BSD-3-Clause](https://github.com/multiview-stitcher/multiview-stitcher/blob/main/LICENSE). The official documentation states that non-rigid transformations are currently unsupported; global registration can slow down with hundreds of tiles or more. The API is evolving, so pin a version. This is a composable stitching component, not a substitute for every BigStitcher capability. |
| **Cellpose / Cellpose-SAM** · [GitHub](https://github.com/MouseLand/cellpose) · [3D segmentation](https://github.com/MouseLand/cellpose/blob/main/docs/do3d.rst) · [Distributed Cellpose](https://github.com/MouseLand/cellpose/blob/main/docs/distributed.rst) · [Model documentation](https://github.com/MouseLand/cellpose/blob/main/docs/models.rst) | Cell/nucleus segmentation, training with human feedback, and 3D segmentation. Large volumes can be divided into overlapping blocks and merged into Zarr labels. The official June 2026 update provides `cpsam_v2`, `cpdino`, and `cpdino-vitb`. | Send candidate labels to a manual review queue, set anisotropy from the actual z/xy sampling ratio, and validate representative ROIs before expanding inference across large datasets. | [Code: BSD-3-Clause](https://github.com/MouseLand/cellpose/blob/main/LICENSE). The README states that all models were trained on CC-BY-NC data, and the annotated dataset is also CC-BY-NC. Check the terms for training data, individual weights, and third-party backbones separately; the code license does not establish unrestricted commercial use of every weight file. The default 3D approach predicts on orthogonal 2D slices and then runs 3D dynamics, which the documentation calls 2.5D. It is not a general model for arbitrary organs or clinical use. |
| **vedo** · [GitHub](https://github.com/marcomusy/vedo) · [Official documentation](https://vedo.embl.es/) | Scientific 3D visualization based on VTK/NumPy: volume slicing, cropping, volume rendering, isosurfaces, and mesh operations; area and volume calculations; mesh or scene export. | Link voxels, surfaces, and object tables through the same physical coordinates. Save presentation parameters such as camera, opacity, and color scale to make research figures reproducible. | [MIT](https://github.com/marcomusy/vedo/blob/master/LICENSE). Smoothing, hole filling, and simplification change geometry. Measure calibrated labels or geometry without presentation processing. Interpretation of mesh volume also requires checking closure, orientation, duplicated vertices, and related conditions. |

## Large-data extensions and resource planning

[BigStitcher-Spark](https://github.com/JaneliaSciComp/BigStitcher-Spark) extends BigStitcher by distributing stages such as resampling, interest-point detection, matching, solving, and fusion across a workstation or cluster. Results from each stage can be inspected interactively by reopening the XML. GUI and Spark capabilities are not identical. Its repository contains both a [BSD 2-Clause license](https://github.com/JaneliaSciComp/BigStitcher-Spark/blob/main/LICENSE) and a [GPL-2.0 file](https://github.com/JaneliaSciComp/BigStitcher-Spark/blob/main/LICENSE.txt); check the applicable components when combining or redistributing them.

No single fixed VRAM figure covers this workflow. Chunk size, overlap, channel count, bit depth, concurrency, and 3D extent all change memory requirements. The Cellpose README gives a starting system RAM requirement of 8 GB; larger images and 3D volumes may require 16–32 GB. This does not guarantee capacity for every dataset. A GPU can speed up segmentation. Its distributed module currently requires Zarr input and the Python API; the GUI or browser demonstration should not be treated as already providing this capability.

## Our combined design and its boundaries

The following are proposed combinations in this project, not promises of a unified product already implemented by the upstream repositories:

1. **Global 3D + ROI review at the original resolution**: Use different data-reading budgets for global navigation and local verification, while retaining a route from surfaces back to original slices.
2. **QC determines subsequent nodes**: Missing metadata, registration anomalies, low-contrast regions, and block-boundary conflicts go to review. Thresholds require calibration on real samples.
3. **Labels support measurement; meshes support presentation**: Display simplification must not overwrite the measurement basis or let an attractive surface change quantitative conclusions.
4. **Evidence packages and version records**: Record data checksums, software and model versions, physical units, parameters, transformations, manual edits, and review status.

This route focuses on genuinely acquired volumetric data. 3D assets generated from an ordinary single photograph, generative completion, and synthetic demonstrations are not experimental measurement evidence. The tumor-cell and microenvironment examples are research plans; spatial proximity or marker co-occurrence does not by itself establish interactions, mechanisms, or treatment causality. Without real samples and validation, no research finding or clinical conclusion is claimed.
